# v0.2A.1 Chat → Work Handoff — Verified Labels, Coverage, and QC Evidence

## Goal

Make Vehicle QC's labels, training evidence, and QC outputs trustworthy enough that later manager metrics and specialized ML can be evaluated honestly.

## Product problem

The current workflow uses useful defaults and suggestions to reduce entry time, but those values can become ambiguous if downstream systems cannot tell whether a human verified them, a model predicted them, or the UI merely suggested/defaulted them.

Likewise, a technical score/result can be misleading if it does not make clear which checks actually ran, were not applicable, were unavailable, or failed.

## Locked product decisions

- Evidence must distinguish at least **suggested**, **verified**, and **predicted** states where those concepts apply.
- Convenient UI defaults may remain, but a default/suggestion must not silently become verified training truth.
- Human verification must be attributable to the relevant user/actor when identity is available.
- Model predictions must retain model/version provenance where relevant.
- QC/check results must expose applicability/coverage rather than implying every possible check ran.
- Manager-facing aggregate results must not imply complete QC coverage when applicable checks are missing/unavailable.
- Historical data must be preserved additively; do not rewrite old records into stronger evidence states without evidence.
- v0.2A.1 is an evidence/trust checkpoint, not a broad UI redesign or model expansion.

## Work should resolve

- Exact domain/data model for evidence state.
- Which current fields/tables require evidence-state/provenance changes.
- Safe migration treatment for existing historical labels/defaults.
- Transition rules between suggested, predicted, and verified states.
- Whether verification needs separate actor/timestamp/revision fields or normalized evidence records.
- How training dataset export filters/marks unverified examples.
- How current technical score/check result structures should expose applicability and coverage.
- How to preserve API compatibility where practical.
- Automated acceptance tests and fixtures.
- Minimal UI changes needed to communicate evidence state without slowing routine entry.
- Whether any ADR/API-contract update is required.

## Important review targets

Inspect current behavior for:
- Training defaults set to Good/eligible.
- Copy/paste/bulk label workflows.
- Shot-type defaults and inferred/suggested values.
- Training membership/approval.
- Dataset export.
- Existing label revision history.
- Analysis metrics/issues and technical score presentation.
- Review Queue corrections/overrides.
- Active model metadata/provenance.

## Non-goals

Do not implement in A.1:
- PostgreSQL migration;
- full account/role system;
- broad concurrency hardening;
- full manager analytics dashboard;
- new specialized QC model families;
- DigiLot/HomeNet production integration;
- Human Training mode;
- broad visual redesign.

Those remain later checkpoints.

## Product acceptance criteria

A.1 is ready for human acceptance when:
- a reviewer can tell whether important labels are suggested, predicted, or human-verified;
- verification provenance is retained where relevant;
- defaults cannot silently enter training/evaluation as verified truth;
- historical data survives migration without false verification;
- QC output can explain which applicable checks ran and which did not;
- aggregate score/result behavior does not overstate coverage;
- automated tests cover evidence-state transitions and dataset/export behavior;
- Work independently verifies the implementation before owner testing.

## Human attention

**Human Need:** UX/product acceptance after AI verification.  
**Estimated Human Time:** 15–30 minutes.  
**Blocking:** Yes; A.1 blocks evidence-safe A.2/B/ML work.

## Required Human Test Packet

Batch into one session where practical:
- inspect a new/defaulted training example before verification;
- explicitly verify/correct it;
- inspect a model-predicted value if available in fixture/demo flow;
- confirm dataset/training eligibility behavior;
- inspect one QC result with full coverage;
- inspect one result with an unavailable/not-applicable check;
- confirm the UI does not imply stronger evidence than actually exists.
