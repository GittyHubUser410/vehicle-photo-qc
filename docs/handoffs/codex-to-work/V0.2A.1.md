## 1.0 Implemented scope

Stored values, evidence and approval intent are separate. Imports (including staged imports and explicit sequences), promotion, membership, and Good defaults create suggested evidence. Ordinary saves do not certify changed values. Explicit `verify_fields` confirms only selected training fields, including same-value confirmation, with attributable server timestamps/revisions. Unrelated edits preserve valid evidence. Operational shot confirmation has separate evidence/history and cannot certify training labels.

Paste invalidates copied quality evidence even for equal values, preserves target shot evidence and revokes approval. Operational value changes retain existing training synchronization, but invalidate that training shot evidence and approval. Same operational value changes/confirmations do not overwrite an independently edited training shot. Trash/membership restoration retains histories and does not reapprove. Review decisions never verify labels. UI issue styling no longer treats training approval as review resolution.

New exports use schema 2 and include only active, approved, known, verified shot labels. Quality defaults need not be verified for a shot dataset. Readiness, dashboard and API responses distinguish approval from exportability. Training/evaluation reject schema 1 before model/metric writes, with reverify/re-export instructions. Historical artifacts/models remain intact. Schema-2 consumers validate registered hash/content, image hashes and leakage; training excludes stale/revoked live shot evidence without substituting values, while evaluation retains verified frozen-snapshot semantics.

New runs snapshot operational evidence/revision, prediction/model/run provenance and structured check applicability, execution and outcome. Verified operational labels take precedence over confidence-gated predictions; suggestions alone do not establish coverage. The 0.8 gate and technical score arithmetic remain unchanged. Count checks run independently of unresolved labels. Unavailable detectors, errors and unknown applicability do not pass. Historical runs have unknown evidence. Operational edits/confirmation or pending/failed analysis make completed coverage stale until reanalysis, without rewriting run history.

Existing screens now show provenance badges, separate model suggestion/confidence, explicit operational confirmation, Verify selected labels / Verify + next, export exclusions, structured check detail and stale/historical warnings. Good defaults and the approval checkbox remain convenient; ordinary Save labels remains available.

## 3.0 Migration and recovery evidence

Migration 1/2/3 → 4 is additive and transactional through table creation and final stamp. Fresh initialization uses the shared schema constant after successful creation. Every upgrade first makes a unique SQLite backup, validates integrity/version, checkpoints and closes its connections; existing backup names are never silently reused. A version change during backup causes failure before schema mutation. Future schemas and unversioned populated databases fail closed.

Disposable fixtures compare every pre-existing column projection and row, foreign-key integrity, IDs/relations, rules, custom catalog/sequence records, reviews/revisions, manifests and model metadata. Original/thumbnail/manifest/model hashes remain identical. Legacy approved/nonempty-actor/revision>0 records and revisions receive only legacy-unverified evidence. Migrated training Trash preserves its exact state, and restore remains unapproved/unverified. Repeated migration adds no history or backups. Failure injected immediately before the stamp leaves the original schema and rows intact; the verified backup remains usable.

Full pre-upgrade folders were copied and restored into separate disposable directories; restored schema versions, rows and artifact hashes match.
