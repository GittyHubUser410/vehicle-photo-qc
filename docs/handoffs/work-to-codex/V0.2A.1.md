## 3.0 Data and API requirements

Implement the schema and transitions from the architecture review. Add versioned `shot_evidence`, `shot_revision`, operational shot history, per-field `label_evidence` on current training records and revisions, and immutable run check snapshots. Evidence timestamps and authenticated actor/model/run provenance are server-produced, not accepted as authoritative client fields.

### Requests

- Extend `LabelInput` with `verify_fields: list[str] = []`. Allow only label keys excluding `note`; reject duplicates/unsupported keys. Existing `revision` is mandatory for safe updates as now. Ordinary saves do not verify. Explicit UI confirmation sends the exact reviewed field set. Unknown values may be honestly recorded but cannot become valid model targets.
- Extend `ShotInput` with `verify: bool = False` and optional `revision`. Confirmation requires matching `Photo.shot_revision`. New UI sends revision for all shot changes; stale supplied revisions return 409. A legacy write without revision may save an unverified suggestion, never verify. Such a change invalidates corresponding dependent evidence/readiness.
- Keep import, membership, promotion and paste schemas compatible; none implies verification. No automatic verification from a populated import sequence.
- Keep request `actor` for compatibility/local declaration. Remote verification uses validated request identity; distinguish `authenticated`, `local_declared`, and `system` actor basis.
- All multi-target writes retain atomic stale-target rollback. No batch verification endpoint required in A.1; preserve Save + next with explicit confirmation wording for fast curated entry. Do not reinterpret old Save or the preselected approval checkbox as confirmation.

### Responses

- Keep existing fields/values (`eligible`, `shot_type`, labels, numeric score, legacy string checks). Add evidence, `exportable`, exclusion reasons, and scoped structured QC results. `eligible` remains approval intent; current `training_count` may remain membership count but label it honestly. Add verified/exportable counts for readiness.
- Keep `/api/sequence` as suggestion-only. Historical `checks` remain readable, but new UI shows unknown historical evidence when the new run envelope is absent.
- New structured envelope includes `evidence_schema_version`, `run_id`, `score_scope=technical_baseline`, `coverage`, freshness, and check records. Coverage complete does not mean all outcomes pass or human-approved.
- Snapshot operational evidence/revision used by each measurement. Shot edits/confirmations affecting evidence mark current coverage stale until a new run; do not rewrite historical run records.
- Update explicit response schemas/types and generated OpenAPI for new request/response shapes; do not represent structured objects using the old `Record<string,string>` field.

### Dataset compatibility

New schema 2 exports require current verified shot evidence and existing active/approval conditions. Preserve relevant per-field evidence in the snapshot. Schema 1 remains inspectable only; train/evaluate fail before writes with actionable reverify/re-export instructions. `respect_trash=False` is not a trust bypass. Existing active models continue operating with honest legacy provenance.

Keep integrity and leakage checks. Training excludes currently revoked/changed relevant evidence rather than silently substituting values; evaluation uses immutable verified snapshot evidence and validates registered manifest hash/content. Neither action rewrites old manifests or old metrics during migration.
