# v0.2A Codex implementation specification

## Execution status — umbrella specification

This document remains the detailed **v0.2A scope reservoir**, but it must **not** be handed to Codex as one monolithic implementation task.

Following the strategic review, v0.2A is split into:

### v0.2A.1 — Verified labels, coverage, and QC evidence
Complete first:
- suggested / verified / predicted evidence states;
- provenance for actor/model/timestamp/revision where relevant;
- UI defaults must not silently become verified training ground truth;
- explicit check applicability/coverage;
- result/score semantics that distinguish checked, unchecked, unavailable, and not-applicable checks;
- additive preservation/migration tests for historical labels/training state.

### v0.2A.2 — Small-team production foundation
Only after A.1 passes:
- PostgreSQL transition;
- multi-user concurrency;
- durable analysis-job ownership/queueing;
- accounts/roles/permissions;
- audit trail;
- Windows startup/recovery;
- backup restoration;
- migration/data-integrity evidence.

Work should create bounded Work → Codex handoffs for each checkpoint rather than executing this umbrella spec directly.

## Objective

Harden the current single-PC prototype into a reliable small-team pilot foundation without changing the app's overall look or replacing existing workflows.

Target operating case:

- Approximately 10 named users.
- PC and phone browser access.
- Normal concurrent browsing/review.
- Rare bursts of 3–4 concurrent vehicle uploads.
- One Windows host PC during the pilot.
- Existing Cloudflare Access/tunnel remains the remote-access layer.

## Non-goals

Do not implement in v0.2A:

- photographer analytics dashboards,
- human training mode,
- predictive workload,
- HomeNet/DigiLot integration,
- full SaaS tenancy,
- live AR,
- billing,
- full DigiLot replacement,
- unrelated visual redesign.

## Required preservation

Do not reset or discard:

- existing SQLite database,
- photos,
- thumbnails,
- review history,
- training examples,
- label revisions,
- dataset manifests,
- trained model files,
- dealership/group standards,
- remembered sequences,
- shot-type catalog,
- trash state,
- Cloudflare config.

## 1. Database / PostgreSQL support

Implement a deliberate migration path from the existing schema-v3 SQLite database to PostgreSQL.

Requirements:

- Keep domain models consistent between SQLite and PostgreSQL where practical.
- Do not assume SQLite-only SQL in shared application paths.
- Isolate engine-specific behavior behind small adapters/helpers.
- Provide a migration tool or documented command that:
  1. validates the source SQLite database,
  2. creates/updates PostgreSQL schema,
  3. copies rows in dependency-safe order,
  4. preserves IDs and timestamps,
  5. verifies row counts and critical relationships,
  6. does not copy photos/model bytes unnecessarily,
  7. can be rerun safely only when explicitly supported, otherwise fails clearly.
- Preserve SQLite as a supported local/test backend unless doing so creates unreasonable complexity.
- Do not simply change the connection string and call the migration complete.

## 2. Concurrency hardening

Review every write path for concurrent use.

At minimum:

- vehicle upload creation,
- staged upload mutation,
- photo reordering,
- vehicle metadata editing,
- review resolution/notes,
- training-label edits,
- training membership changes,
- shot-type management,
- delete/restore operations,
- dealership/group rule changes.

Requirements:

- Use transactions correctly.
- Continue optimistic concurrency where already used.
- Add revision/version protection to other high-risk shared-edit surfaces where useful.
- Avoid global process locks for operations that should be safe at database level.
- Preserve idempotent upload receipts/retry behavior.
- Never allow photos from two upload batches/users to mix.

## 3. Job queue / analysis isolation

The current background worker is in-process and the app is intentionally one Uvicorn worker.

For v0.2A:

- Introduce a clear job abstraction for analysis.
- It is acceptable to keep the pilot worker local, but processing must be isolated enough that queued analysis does not block API responsiveness.
- Job ownership/state must remain durable across app restart.
- Multiple submitted vehicles should queue safely.
- Prevent the same shoot from being analyzed concurrently by duplicate workers.
- Document the path to an external worker/queue later; do not overbuild distributed infrastructure yet.

## 4. User accounts

Add real application users rather than relying only on Cloudflare email identity.

Initial roles:

- Admin
- Manager
- Reviewer / Trainer
- Standard User

Requirements:

- Map authenticated Cloudflare identity to an application user.
- Keep local-development/test authentication usable without real Cloudflare.
- Do not expose a public anonymous production mode.
- Admin can manage users and roles.
- Role checks must be enforced server-side, not only hidden in the UI.
- Keep permission rules simple and documented.

Suggested first-pass permissions:

- Admin: all actions, user management, setup.
- Manager: dealership/rules, reviews, metadata, reporting, training management.
- Reviewer/Trainer: review and training-label workflows.
- Standard User: upload, browse allowed content, own operational workflows; no destructive administration.

If current pilot expectations require equal permissions temporarily, preserve a safe compatibility path but do not make it the long-term default.

## 5. Audit trail

Record who performed important actions.

At minimum:

- vehicle metadata edits,
- shot-label edits,
- training-label edits,
- training approval changes,
- review resolve/reopen/notes,
- delete/restore,
- dealership/rule changes,
- shot-type rename/archive/reorder,
- user-role changes.

Audit records should contain:

- actor/user ID,
- action kind,
- target kind/id,
- timestamp,
- concise before/after or structured change payload where appropriate.

Avoid logging secrets or full image data.

## 6. Windows startup / recovery

The pilot host should recover without manually reopening terminals.

Requirements:

- Document BIOS/UEFI prerequisite: Restore AC Power Loss / AC Power Recovery = Power On.
- Provide a supported Windows startup method for:
  - Vehicle QC backend,
  - analysis worker if separate,
  - Cloudflare tunnel.
- Prefer startup/service behavior that does not depend on an interactive desktop login where feasible.
- Preserve environment/config secrets without checking them into Git.
- Provide stop/restart/status instructions.
- Do not make smart-plug hard power-off the normal shutdown procedure.

## 7. UI constraints

- Keep present visual design.
- Do not redesign navigation.
- Add user/account UI only where necessary.
- Preserve mobile portrait fixes.
- Preserve searchable shot-type picker and library editing.
- Keep forms usable on Android and desktop.

## 8. Compatibility

The app should still support:

- existing imported vehicles,
- existing photo downloads,
- existing training datasets,
- existing active model metadata,
- schema history,
- current Cloudflare Access flow,
- direct local development at localhost.

Codex should finish v0.2A with:

1. Code changes.

3. User/role documentation.
4. Startup/recovery documentation.
5. Updated architecture doc.

7. A short implementation summary listing:

Do not start v0.2B.
