# Vehicle QC v0.2 roadmap

## Purpose

v0.2 is a release family, not one giant implementation task. It should improve production reliability, manager visibility, and human training without destabilizing the presentable v0.1 pilot.

New ideas may be documented here, but major new feature families should normally remain deferred until pilot feedback supports them.

## Product principles

1. Do not force field agents to use two separate shooting/workflow apps.
2. Vehicle QC should either:
   - integrate behind the current DigiLot/HomeNet workflow, or
   - eventually replace DigiLot only when it can cover photo organization/storage, HomeNet upload, label printing, and invoicing reliably.
3. Every major feature should do at least one of:
   - reduce labor,
   - prevent mistakes,
   - improve management visibility/accountability,
   - replace a paid operational tool.
4. Prefer incremental migrations over rewrites.
5. Protect existing photos, labels, trained models, datasets, dealership rules, and review history.
6. Pilot evidence may reorder priorities.
7. **Shot-aware model routing is a core architecture principle:** identify the shot type first, then run only the deterministic checks and specialized models relevant to that photo. Do not run every model on every image.
8. Keep normal review UI simple; detailed ML diagnostics, training controls, routing information, and model history belong in Settings / Advanced Model Center.

## Difficulty and value scale

- Difficulty 1/5: small UI/data change.
- Difficulty 2/5: straightforward feature.
- Difficulty 3/5: moderate multi-component work.
- Difficulty 4/5: major architecture/integration work.
- Difficulty 5/5: substantial product/research effort.

- Value 1/5: minor convenience.
- Value 3/5: meaningful operational benefit.
- Value 5/5: core product/business value.

## v0.2A — Production foundation

**Goal:** make the current app safe and reliable for a small team and for later v0.2 features.

### Approved scope

- PostgreSQL migration path and production database support.
- Preserve SQLite compatibility for backup/transition where practical.
- Safe multi-user concurrency.
- Support approximately 10 users with rare bursts of 3–4 concurrent uploads.
- Queue analysis work so one user's upload does not block ordinary browsing/review.
- Individual user accounts.
- Account/organization architecture must anticipate future **external dealer users** scoped to one dealership or dealer group; do not assume every authenticated user is an employee.
- Initial roles:
  - Admin
  - Manager
  - Reviewer / Trainer
  - Standard User
- Audit trail for important changes:
  - labels,
  - approvals,
  - deletes/restores,
  - metadata corrections,
  - review overrides.
- Startup / recovery hardening for Windows host.
- Preserve Cloudflare Access/tunnel approach for the pilot.
- Prepare model-provenance/data structures so future explanations can resolve model version → dataset → training example and optionally store embeddings. Do not build the explanation UI in v0.2A.
- Add a staged **Settings** area with clean navigation for General, Account, Users & Roles, System, and Models. Keep model information high-level at first.
- Role-gate Settings features server-side. Standard users should see personal/general settings; Admin/Manager/Reviewer roles gain only the controls appropriate to them.
- Preserve room in the model metadata for model purpose, applicable shot types, model version/status, training dataset, activation history, and future routing/threshold configuration.
- Pilot-discovered high-priority defects may be included if they block safe use.

**Difficulty:** 3/5  
**Value:** 5/5

## v0.2B — Management intelligence

**Goal:** convert QC data into manager labor savings and accountability.

### Approved scope

- Photographer performance dashboard.
- Vehicle/photo volume by photographer.
- Average technical score.
- First-pass acceptance rate.
- Reshoot rate.
- Recurring error analysis by photographer.
- Dealership performance comparisons.
- Time trends.
- Missing-shot / completeness auditing.
- Duplicate and near-duplicate detection.
- Basic vehicle workflow status:
  - Needs photos
  - In progress
  - Uploaded
  - QC processing
  - QC issue
  - Reshoot
  - Approved
  - Delivered
- Manager filters by employee, dealership, date range, status, and issue type.
- **Explain / False Positive v1** for ML-driven review decisions:
  - identify which subsystem triggered review,
  - show active model/version and confidence,
  - show nearest/relevant training examples in a carousel,
  - show similarity score / neighbor rank rather than claiming exact causal percentage,
  - open a large training-example view with labels, provenance, dataset/model membership, and vehicle context,
  - allow authorized users to correct labels or exclude an example from future training,
  - record false-positive feedback and count corrections made since the active model was trained.
- Store/reuse model embeddings for approved training examples when practical so nearest-example lookup is inexpensive.
- Expand **Models** settings for managers/admins with active and historical model versions, purpose, applicable shot types, training date/dataset, simple performance trends, false-positive feedback, training-data health, and model timeline/history.
- Keep ordinary review pages concise: show a simple model result/confidence with a **View details** link into the relevant advanced model information.

**Difficulty:** 2–3/5  
**Value:** 5/5

## v0.2C — Human Training Mode

**Goal:** let new agents practice independently using dealership-specific visual guidance, then receive automated QC and manager coaching.

See [V0.2-HUMAN-TRAINING-MODE.md](V0.2-HUMAN-TRAINING-MODE.md).

### Additional approved v0.2C data/architecture work

- Collect structured labels for future specialized checks where useful: headrest state, seat position, reflection type/presence, interior alignment, and listing-consistency outcomes.
- Connect Human Training configuration/reference libraries to Settings without exposing technical ML controls to trainees.
- Reuse training/reference examples across human training and model-debugging workflows where appropriate.

**Difficulty:** 3/5  
**Value:** 5/5

## v0.2D — Integrations and operational polish

### Approved investigation / likely scope

- Deeper inventory/workflow tracking.
- DigiLot/HomeNet integration research.
- Automatic approved-media delivery if APIs/feeds permit.
- Delivery/error tracking.
- Wrong-vehicle / photo-set mismatch detection if model/data are ready.
- Automatic body-style suggestion as a low-risk stretch feature.
- Mobile refinements based on actual pilot use.
- Keep the first Human Training camera workflow browser-based unless field testing shows the browser is the actual constraint.
- Preserve a clean separation between Human Training data/workflows and the camera-capture client so a future native Android app can replace web capture without rebuilding sequences, references, annotations, trainee history, QC, or manager review.
- Prepare customer-facing data boundaries so future dealer users can see only their authorized dealership/group data, never internal employee rankings, private manager notes, other dealers, or advanced ML controls.
- Introduce/validate specialized **shot-aware model pipelines** as training data becomes sufficient. Candidate checks include:
  - vehicle color vs listing color,
  - interior camera alignment/orientation,
  - headrest position,
  - seat position/staging,
  - reflection detection for people/cameras/phones,
  - exterior angle/framing improvements.
- Interior alignment should distinguish at least roll/level from directional/framing errors; use deterministic geometry where reliable and specialized ML for shot-specific yaw/pitch/framing judgments.
- Run reflection detection only on relevant reflective shot types; allow local-model confidence to route ambiguous cases to an LLM instead of scanning every photo with an LLM.

**Difficulty:** 4/5  
**Value:** 4–5/5

## Dealer portal / customer-facing product layer

**Status:** approved future direction; do not build full portal in v0.2A–C.

### First dealer-facing release — likely v0.2D / v0.3

- Read-only dealer login/dashboard scoped to dealership or dealer group.
- Vehicle/photo/QC visibility for the dealer's own inventory.
- Quality trends over time.
- First-pass acceptance, reshoot rate, sequence completeness, and dealer-standard compliance.
- Simple separation between **technical quality** and **dealer-standard compliance**.
- Drill-down from dashboard metrics into affected vehicles/photos.
- Dealer-facing SLA/service metrics where available: turnaround, backlog, completion rate, reshoot turnaround.
- Dealer-group hierarchy support with group-level visibility and location-level scoping.

### Later dealer self-service

- Dealer-defined shot sequences and preferences.
- Reference-image standards per shot type.
- Structured requests such as headrest position, seat staging, framing/angle preferences, banner policy, reflection tolerance, minimum photo count, and listing-consistency checks.
- Structured issue/request workflow tied to example photos rather than relying on email/text descriptions.
- Versioned standard changes with effective dates and audit history.
- Optional manager approval/validation before a dealer-submitted change becomes active.
- Dealer Group Admin / Dealer Location Admin / Dealer Viewer roles.
- Periodic dealer-facing reports summarizing quality, compliance, reshoots, turnaround, and incorporated requests.

### Dealer portal design principle

Dealers configure the **desired outcome**, not technical ML parameters. The internal system translates dealer requirements into rules, reference sets, routing, and training guidance. Dealer users should not retrain models, activate models, edit confidence thresholds, see other customers' data, or see internal employee-performance/disciplinary information.

## Independent model lifecycle and retraining health

**Status:** approved ML architecture principle.

- Each specialized model family is trained and versioned independently unless a future deliberate multi-task architecture replaces that design.
- Examples of independent model families: Shot Type, Exterior Angle, Interior Alignment, Headrest, Seat Position, Reflection, Framing, Listing/Color Consistency.
- A single training photo may supply labels to several model families, but each model consumes only its relevant label(s) and applicable shot types.
- Training applicability and inference applicability should use the same shot-aware routing rules.
- Do not retrain every model whenever new data arrives.
- New approved examples and corrections accumulate until a model-family-specific retraining trigger is reached.
- Retraining produces a **candidate** model; the active model remains unchanged until validation and deliberate activation.
- Preserve previous active model versions for rollback.

### Model health / retraining signals

The Advanced Model Center should monitor each model family independently for:

- new approved examples since last training,
- corrected false positives / false negatives,
- human/model disagreement rate,
- confidence distribution changes,
- LLM escalation rate,
- performance by dealership,
- performance by shot type,
- performance by body type,
- coverage balance across good/bad labels and relevant contexts,
- distribution/data drift indicators.

The system should progress from simple warnings such as **Retraining recommended** to more specific guidance such as **Collect more rear-seat SUV examples from Dealer C**.

### Model metadata

Store, at minimum:

- model family,
- version,
- architecture/type,
- applicable shot types,
- labels used,
- training dataset ID,
- example count,
- training date,
- validation/holdout metrics,
- activation date/status,
- previous version,
- retraining-health metrics/triggers.

Near term, prefer separate specialized models because they are easier to train, debug, explain, version, and roll back. Revisit shared-backbone / multi-task models only when dataset scale and measured compute/performance benefits justify the added coupling.

## Native Android capture strategy

**Status:** likely v0.3+; trigger-driven rather than date-driven.

### Browser first — v0.2C / v0.2D

The existing HTTPS web app should support the first useful Human Training experience: live camera preview, reference/ghost overlays, instructions/annotations, sequential capture, upload, and post-capture QC. Continue with web capture through v0.2D unless real field use shows major limitations.

### Native Android trigger conditions — likely v0.3+

Build a native Android capture client when one or more of these become important enough to justify it:

- reliable offline capture and later synchronization,
- tighter camera control such as focus/exposure/lens/resolution/flash behavior,
- continuous gyroscope/accelerometer/compass use,
- ARCore-based spatial guidance,
- real-time move-left/right/closer/farther coaching,
- high-frequency on-device computer vision,
- automatic capture when alignment is acceptable,
- robust background upload/retry behavior,
- predictable camera/session behavior across supported devices.

### Proposed mobile architecture

Keep the server-side sequence library, dealership standards, reference images, annotations, trainee history, QC, users, and manager review independent of the capture client. A future Android app should consume the same APIs and data model rather than creating a parallel training system.

Use lightweight on-device ML for immediate guidance where practical, then send captured photos to the server for full-quality QC. Android should be the first native platform because the field device fleet is primarily Android; evaluate iOS only after Android proves the native-capture value.

## PC Operations / ML Console strategy

**Status:** optional operational tooling; evaluate during v0.2D, likely fuller implementation in v0.3+.

### Near-term — v0.2D candidate

Before building a native Windows application, consider a **local-only admin web interface** that reuses the existing frontend/backend stack. Possible controls:

- backend/worker/database/tunnel health,
- storage and backup status,
- job queues and failed jobs,
- model-training job status,
- GPU/system utilization,
- logs and diagnostics,
- basic model activation/rollback controls where authorized.

This is the lowest-cost way to validate whether a dedicated operations interface creates enough value.

### Native PC application — v0.3+ if justified

A dedicated Windows/desktop application becomes useful when Vehicle QC needs deeper local-machine integration such as:

- bulk USB/network-folder photo ingestion,
- folder watching and automated validation,
- offline/local processing and later synchronization,
- high-volume keyboard/multi-monitor review,
- local model training and GPU scheduling,
- dataset/model inspection,
- service control, backups, storage management, and system recovery,
- managing local AI agents and sharing GPU resources between production inference, training, and development tasks.

The desktop app should complement, not replace, the web app. The recommended long-term split is: web for managers/dealers, Android for advanced field capture, and desktop/local console for operations, ML, bulk ingest, and diagnostics.

## Deferred to v0.3+ / data-dependent

- Predictive dealership workload.
- Employee-capacity forecasting.
- Expected completion-time forecasts.
- Live AR guidance such as move left/right/closer/farther.
- Automatic pre-capture framing score.
- Auto-shutter when aligned.
- Sensor-assisted positioning.
- Robust offline capture/sync.
- Native Android capture client when Human Training needs ARCore, real-time local ML guidance, advanced camera control, automatic capture, or dependable offline/background behavior.
- Native PC Operations / ML Console if the local-only admin web interface becomes insufficient for filesystem, USB, GPU, service, or local-agent integration.
- Full DigiLot replacement.
- Standalone billing tracker unless Vehicle QC becomes the primary field workflow.
- Advanced ML explainability: Grad-CAM/feature-attribution heatmaps, influence-function-style training-example ranking, automated mislabeled-example/outlier detection, training-cluster diagnostics, and model-to-model explanation comparison.
- Full **Advanced Model Center**: shot-aware pipeline visualizer, model-by-model health metrics, confusion matrices/common confusions, confidence distributions, version comparison, performance by dealership/shot/body type, LLM escalation rate, detailed training-data health, model timeline, candidate-vs-active comparison, and advanced training controls.
- Admin-only routing/threshold configuration after the pipeline is mature enough to expose safely; initial routing views should be diagnostic/read-only.
- Advanced local-model training controls (epochs, batch size, learning rate, class weighting, augmentation, thresholds) behind an expert/advanced mode; recommended training remains the default.

## Forecasting concept

Later, after enough clean operational history exists, combine:

- dealership vehicle counts,
- historical arrival patterns,
- day/time/season,
- employee throughput,
- reshoot rates,
- assignment history,
- availability,

to estimate:

- expected incoming workload,
- likely completion timing,
- whether an agent is likely to be overloaded,
- where management may need to rebalance assignments.

Do not implement forecasting before enough reliable history exists.

## Decision log

### Keep v0.1 stable during initial pilot
Reason: real-user feedback is more valuable than speculative architecture work.

### Do not prioritize standalone service billing
Reason: it adds limited value if agents must still use DigiLot as their primary workflow.

### Performance/accountability is core
Reason: it creates direct manager value from data already produced by QC.

### Forecasting is later
Reason: useful prediction requires clean historical data.

### Human Training Mode is approved for v0.2
Reason: it reuses dealership sequences, photo taxonomy, QC analysis, review queues, and employee history.

### Explain / False Positive v1 belongs in v0.2B
Reason: managers need a practical way to understand ML-driven flags and repair bad training examples. The first version should use nearest/similar training examples and model provenance rather than pretending to know an exact causal percentage for each training photo.

### Training-image retention should be separate from ordinary operational retention
Reason: model weights do not contain recoverable copies of training photos. Operational originals may expire, but approved ML/reference examples should retain either the original or a reduced training/reference copy plus labels, hash, provenance, and embedding while they remain relevant to active/historical models.

### Hybrid AI is the long-term default direction
Reason: deterministic checks and specialized local vision models are inexpensive and consistent at high volume; multimodal LLMs are better reserved for ambiguous cases, explanation, and semantic reasoning where their extra cost adds value.

### Shot-aware routing is a core architecture decision
Reason: each photo type has different meaningful checks. Classify the shot first, then run only applicable technical checks and specialized models. This reduces compute, false positives, and unnecessary LLM calls while making every decision easier to explain and troubleshoot.

### Interior alignment is a dedicated model/check family
Reason: interior photos also have valid camera direction, pitch/yaw, roll/level, and framing requirements. Use deterministic geometric checks where reliable, and specialized shot-specific ML for direction/framing judgments. Do not assume exterior-angle logic transfers directly to interiors.

### Settings / Advanced Model Center is approved as a staged application feature
Reason: normal users need a clean interface, while managers/admins need a place to inspect model purpose, pipelines, training history, versions, performance, false positives, and system health. Build the Settings shell in v0.2A, expand model diagnostics in v0.2B, connect training settings in v0.2C, and reserve full pipeline tuning/training controls for v0.2D/v0.3.

### Specialized model families train independently
Reason: each model has a narrow task, applicable shot types, labels, performance profile, and retraining need. New data for one model should not force unrelated models to retrain. Candidate models must be validated before activation and older versions retained for rollback.

### Vehicle QC should identify when a model needs more data or retraining
Reason: reviewer corrections, disagreement, confidence drift, LLM escalation, dealership/body-type weakness, and training-data coverage can reveal exactly where a model is degrading or underrepresented. The system should eventually recommend specific data collection rather than only saying a model is inaccurate.

### Dealer portal is an approved future customer-facing layer
Reason: giving dealerships visibility into their own photos, quality trends, compliance, service performance, and eventually structured standards can reduce manager communication overhead and create direct customer value. Start read-only before self-service configuration, and keep dealer permissions/business language separate from internal ML administration.

### Web Human Training first; native Android only when browser limitations are real
Reason: the browser is sufficient to validate reference-guided training and post-capture QC. Native Android becomes worthwhile when real-time spatial guidance, ARCore, advanced camera control, local ML, offline capture, or background synchronization materially improve field performance.

### Keep capture clients replaceable
Reason: sequences, dealership standards, references, annotations, trainee history, QC, and manager review should live in shared backend/domain services so web capture can later be replaced by Android without rebuilding Human Training.

### PC application is an operations tool, not the primary user interface
Reason: normal manager/dealer access remains better on the web. Start with a local admin web console in v0.2D if operational complexity grows; build a native desktop console in v0.3+ only when deeper OS/filesystem/GPU/local-agent integration provides clear value.

### Avoid a partial DigiLot replacement
Reason: adoption friction could outweigh QC value if agents must duplicate work.
