## 1.0 Outcome

A.1 can be implemented additively within the present SQLite/FastAPI/React architecture. No account system, PostgreSQL migration, new classifier, or distributed queue is needed. The central distinction is **value versus evidence versus permission to use that value for training**. These are separate concepts; a single approved boolean cannot represent all three.

No blocking product/security/data decision was found beyond the locked Chat decisions. Preserve Good defaults and selected approval intent, but require an explicit verification action for evidence. Human UX acceptance remains required after independent Work verification. The UI changes are badges, concise check status, and explicit confirmation actions in existing screens, not a new visual flow requiring a new Figma design.

## 3.0 Domain decision

### 3.1 Label evidence

Use a versioned evidence envelope: `state`, `source`, `value`, `value_revision`, `recorded_at`, `actor_id`, `actor_display`, `actor_basis`, and optional source reference. States: `suggested`, `verified`, `legacy_unverified`. Predictions remain separate run-scoped evidence with state `predicted`, model ID, confidence and run ID. Null/missing evidence never means verified.

`unknown` is a value, not a provenance state. A person can explicitly confirm that a value is unknown, but that does not make it an acceptable classifier target or resolve required-shot coverage. Confidence is not human verification.

Add `Photo.shot_revision` and `Photo.shot_evidence` plus a small append-only `photo_shot_revisions` table for operational shot changes/confirmations. This is separate from `TrainingExample.revision` and `LabelRevision`; the existing two shot fields can intentionally differ.

Add `TrainingExample.label_evidence` JSON keyed by label field and the same snapshot column on `LabelRevision`. Per-field evidence avoids certifying Good defaults when only the shot was confirmed. Continue using one aggregate example revision for optimistic writes; each field records the revision at which its value was asserted. Evidence for unchanged fields may remain valid across unrelated field/note changes. Validity compares field value/revision history, not simply equality with the latest aggregate revision.

Keep `eligible` as the existing approval-intent/exclusion switch. Derive `exportable` from eligibility, live membership, known relevant value, and current verified evidence. Training shot export requires verified `shot_type`; it must not require unrelated quality labels to be verified. Quality readiness counts require verified evidence for their own field. A.1 does not add new quality-model training.

### 3.2 State transitions

| Action | Result |
|---|---|
| Import / suggested sequence / promotion / new membership | Values and Good defaults remain; evidence suggested; exportable false |
| Ordinary save without explicit confirmation | Changed fields suggested; unchanged verified fields retained; actor does not imply verification |
| Explicit confirm fields, including same-value confirmation | Selected fields verified for submitted values; revision increment and attributable history |
| Operational shot confirmation | Operational field verified; training evidence not automatically promoted |
| Model inference | Immutable predicted evidence; never writes human verification |
| Paste | All copied quality fields become suggested even when equal; note is not a training target; target shot evidence preserved; eligibility remains revoked as today |
| Operational shot value changes | Synchronize existing training shot value as today, but mark that training field suggested and revoke eligibility; preserve other field evidence |
| Membership disable / trash | Eligibility revoked, evidence history retained; restore does not silently reapprove |
| Review resolve / false positive / accept | Review history changes only; no implicit label verification or training approval |
| Legacy migration | Preserve values/approval/history; evidence legacy_unverified, never inferred from `labeled_by`, revision number, or old approval |

Remote actor attribution comes from validated `request.state.user` and email; request actor text cannot override it. Local actor labels are allowed but explicitly marked `local_declared`, not authenticated. System actions use `system` attribution and cannot verify human evidence.

### 3.3 Analysis evidence

Resolve operational shot for coverage/routing using verified non-unknown operational value first, otherwise the existing confidence-gated run prediction, otherwise unresolved. Retain the current 0.8 gate; do not tune models in A.1. Predicted coverage must be labeled as predicted, not human-verified. Training-only labels do not silently change operational coverage. Model disagreement with a verified value stays visible but does not override it.

Use structured check records with `check_id`, applicability (`applicable`, `not_applicable`, `unknown`), execution (`completed`, `not_run`, `unavailable`, `error`), outcome (`pass`, `concern`, `unknown`), reason code, scope, input provenance, and rule/model/run identifiers. A missing detector is unavailable, not not-applicable. Failed execution is not a detected defect. Checks not run never pass.

Persist shoot-level check records in new `Run.check_results` and per-photo records/input snapshots in `Measurement.context` under a versioned key. Add `Run.evidence_schema_version`; old runs default to 0. `Shoot.checks` remains a compatibility projection; the new structured envelope is authoritative. Preserve historical results and scores, mark their evidence coverage unknown, and require a new run to obtain new coverage.

Cover the currently advertised registry only: technical blur/exposure/saturation, photo count, required-shot/sequence, shot classification, segmentation, critical crop, angle and banner clearance. Segmentation is an unavailable dependency, not a new implemented detector. Photo count runs independently even when labels are unresolved. General mode skips dealership count/sequence by existing policy. Unconfigured required shots and disabled banners get reasoned not-applicable states, not a claim that configured requirements were satisfied.

Aggregate coverage is complete only when every applicable registered check completed and no applicability is unknown. Complete coverage can contain concerns; it does not mean passed or approved. Mark unavailable/unknown/error/stale inputs explicitly. Do not invent a delivery approval workflow. Technical score stays numerically unchanged and clearly scoped to performed technical checks; do not compute a misleading full-QC percentage.

## 4.0 Migration and historical snapshots

Implement schema 4 as additive SQLite migration, transactionally adding columns/table and version stamp. Fresh initialization uses the shared schema constant after creation; upgrade paths 1→2→3→4 and 2→3→4 must work as well as 3→4. Backup existing databases before changes; use a unique verified backup or refuse to proceed on an ambiguous prior backup rather than silently treating an unrelated file as valid. No migration mutates media, manifests, models, labels, old revision payloads, or review decisions.

New evidence fields on old rows/revisions are legacy-unverified. Do not reconstruct verification from suggestive historical metadata. Re-running migration is a no-op. Unsupported future versions and unversioned populated databases remain fail-closed.

Export manifest schema 2 with `purpose=shot_type`, evidence schema version and per-entry training-example ID, relevant verified evidence, source label revision, approval snapshot, and existing grouping/hash metadata. Preserve existing exact-duplicate and vehicle grouping safeguards.

Keep schema 1 files, models and old metrics readable as historical artifacts. New train/evaluate commands must not consume schema 1 as verified ground truth; fail with a reverify/re-export instruction before model/metrics writes. Provide an explicit read-only legacy inspection mode in the loader for preservation tests/tools; production train/evaluate callers must not enable it. Existing active models are not deleted/deactivated or retrospectively certified.

For schema 2, training continues respecting live trash/eligibility. Also exclude entries whose relevant value/evidence was revoked or changed since snapshot; do not silently substitute current labels. Evaluation retains the existing frozen-snapshot behavior (`respect_trash=False`) but still validates schema-2 evidence and registered manifest integrity. Later corrections do not rewrite historical snapshots; disclose frozen-snapshot semantics. This is not a new retention/deletion policy.

## 5.0 Scope, risk and verification limits

This was source inspection, not runtime proof. No application tests, migration trial, model accuracy measurement, or live-host security assessment were performed for this documentation-only handoff. Codex must implement and provide the acceptance evidence; Work then independently verifies it.

The key risks are schema stamping mistakes, implicit verification through alternate write paths, mutable historical check interpretation, schema-1 loader bypass, and stale edits overwriting evidence. Target those risks with the bounded test plan. Do not expand into A.2 global concurrency/auth redesign or B.2 benchmarking infrastructure.

**Execution guidance:** Difficulty High; Strong model strength recommended because the change crosses migrations, API semantics and ML data consumers. Escalate strength for unresolved transactional or snapshot-integrity failures. Owner intervention before implementation: no new decision required under the locked handoff; UX acceptance remains a 15–30 minute gate after Work verification. Global management policy is unchanged.
