# v0.2A migration and rollback notes

## Core rule

Existing user data is more valuable than convenience. v0.2A must be able to fail without destroying the working v0.1 library.

## Existing state

Current baseline:

- SQLite schema v3.
- Immutable original images stored outside DB rows.
- Thumbnails stored as files.
- Dataset manifests stored as files.
- Model artifacts stored as files.
- Cloudflare remote configuration is local/private and must not enter Git.
- Existing migration backups are database-only and do not replace a full data backup.

## Before upgrade

Require:

1. Stop Vehicle QC.
2. Stop any model-training process.
3. Make a full backup of `QC_DATA_DIR`.
4. Record current code commit.
5. Record current database schema/version.
6. Verify backup can be read.
7. Keep rollback code and data backup together.

## PostgreSQL migration strategy

Preferred approach:

- Treat SQLite as the authoritative source during migration.
- Create PostgreSQL schema from explicit migrations/models.
- Copy relational rows in dependency order.
- Keep generated IDs unchanged.
- Keep file/object paths unchanged for the pilot.
- Validate all copied records before switching application config.
- Only after verification should the app be pointed at PostgreSQL.

Suggested dependency order:

1. users / organizations if added,
2. conglomerates,
3. dealerships,
4. photographers,
5. shot types,
6. dealer sequences,
7. shoots,
8. photos,
9. analysis runs,
10. metrics / issue detections,
11. review queue / events,
12. training examples / revisions,
13. training datasets,
14. model-version metadata,
15. audit records if generated during migration only when appropriate.

Do not rewrite image/model bytes merely because the relational database changes.

## Compatibility approach

During the pilot, supporting both SQLite and PostgreSQL is useful for:

- existing development tests,
- migration validation,
- easy local disposable test environments.

Production/pilot remote multi-user use should prefer PostgreSQL after migration.

## Transaction review

SQLite-specific patterns such as:

- `BEGIN IMMEDIATE`,
- WAL assumptions,
- file-level concurrency expectations,

must be reviewed and replaced with backend-appropriate transactional behavior.

Do not emulate SQLite locking globally if PostgreSQL row/transaction semantics can solve the problem more cleanly.

## Rollback

If PostgreSQL migration or v0.2A startup fails:

1. Stop the new app.
2. Do not modify the source SQLite backup.
3. Restore the matching v0.1 code commit.
4. Point `QC_DATA_DIR` back to the complete pre-upgrade data folder.
5. Restore previous remote startup configuration.
6. Start v0.1 and verify:
   - dashboard,
   - photo library,
   - training library,
   - reviews,
   - uploads.

Avoid down-migrating a live modified PostgreSQL database back into SQLite as the primary rollback plan. Rollback should use the preserved pre-upgrade snapshot.

## Secrets

Never commit:

- Cloudflare Access audience value,
- tunnel credentials,
- database passwords,
- SMTP/API keys,
- user password hashes exported from production,
- private photos/databases/model weights.

Document variable names and sample values only.


## A.1 SQLite schema 4 implementation

A.1 implements only the additive evidence checkpoint, not PostgreSQL/A.2. Supported schema 1, 2 and 3 upgrades run in one explicit SQLite transaction. New columns/table and the final stamp commit together. Fresh creation uses the same schema constant after successful table creation.

Before an upgrade the migrator creates a unique `migration-backups/before-v4-from-v<version>-<uuid>.db` with SQLite's backup API, checks integrity and the source schema version, and refuses to use an ambiguous pre-existing file. This database-only backup is not a substitute for the full stopped-app data backup above. No photos, thumbnails, manifests, model bytes or old metrics are rewritten. Existing label values, approval intent and revision payloads remain; new provenance is `legacy_unverified`. Historical runs remain evidence version 0. Repeated startup is a no-op for migration/history.

Added schema: `photos.shot_revision/shot_evidence`; append-only `photo_shot_revisions`; `training_examples.label_evidence`; matching `training_label_revisions.label_evidence`; and `analysis_runs.evidence_schema_version/check_results`. Per-photo run evidence uses the existing `photo_metrics.context` JSON column.

Rollback rehearsal is automated on disposable full copies: old column projections, IDs/relations, review history, rules/catalog/sequences, artifact hashes and backed-up database integrity are compared before/after; injected failure before the stamp leaves the original schema/data intact. Restoring the complete older copy into another directory preserves its old version and hashes. See `tests/test_evidence.py` and the Codex → Work report.

Do not run old code against a schema-4 database. Stop the app and training, preserve the upgraded folder for reconciliation, then restore the matching code checkpoint and complete pre-upgrade folder into a separate location. New writes after the backup are not present in that restored copy. No in-place downgrade or production restore is authorized here. Working Cloudflare configuration is retained separately and must never enter Git or evidence captures.
